### 已读源码并核实的设计强项（非文档转述）
- `engine/src/bus.ts`：durable 路径 = validate → seq → sink.append → **广播**（先落盘再广播）；seq 分配与 append 同一 per-session promise 互斥链（`st.tail`），单写者是结构保证；`st.tail = task.catch(() => undefined)` 使单次失败不毒化队列。
- `engine/src/tools/pipeline.ts`：每个「未执行」分支都补 `tool.started/completed` 事件对（E_ABORTED / E_MODE_BOUNDARY / E_NOT_FOUND / E_PERMISSION / E_TRUNCATED）；`ProgressGate.close()` 关门排水保证 progress 永不晚于 completed；guard 过滤后同一份输出同时供事件与 toolResult 回喂（不分叉）。
- `engine/src/permission/service.ts`：超时 / turn 中断 / dispose / 级联 / shutdown 五路径统一 resolve(deny)，并记 origin（reply/timeout/abort/shutdown/cascade/mode-change）；`evaluateAll` 任一 deny 短路；无命中默认 `ask`。
- `engine/src/run-loop.ts`：`started` 标志保证 turn.completed 必有配对；截断保护合成 E_TRUNCATED 事件对 + 回喂续跑。

### 发现真实缺陷（待人类决策，**未动手修**）
**maxSteps 触顶路径悬空——工具卡永久「运行中」**
- 引擎侧：`run-loop.ts:382` `turn.step >= maxStepsPerTurn` → `finish='length'` 直接 break，工具**不执行且不补事件对**，而含 toolCall 的 `assistant.message` 已在 `:328` emit（默认 maxStepsPerTurn=40，config.ts:62）。
- 投影侧：`protocol/src/apply-event.ts:474-487` 已为每个 toolCall push `kind:'tool', status:'running'` 项；`closeStreamingOfTurn`（`:261`）只清扫 reasoning/assistant 的 streaming 标记，不碰 tool。
- 表现：`apps/web/src/features/chat/ToolCard.tsx` 对 `status==='running'` 渲染 spinner + 「运行中…」+ 活的 `TerminalView(running)`，无上层兜底 → 永久转圈，回放同样重建。
- 影响面已核实有限：`SessionPage.tsx:150` 的 TurnStatusBar 与 `apps/cli/src/components/Footer.tsx:31` 均由 `activeTurn` 门控，turn.completed 已置 null，故两者不受影响。
- 测试缺口：`engine/tests/run-loop.test.ts:399` 只断言 `tools.batches === 0` 与 `finish:'length'`，**未断言 ProjectionState**。
- 判为遗漏而非取舍：同类问题在截断分支（`run-loop.ts:343`，stopReason==='length'）已用合成事件对解决。

### 其余具体问题
- `pipeline.ts:277` `def.inputSchema.parse(call.input)` 的 zod 错误经 `mapError`（`^E_[A-Z_]+` 正则）匹配不上 → 误归类 **E_INTERNAL**，并把整段 zod JSON 回喂模型；「模型传错参数」是高频失败类别，值得专属错误码 + 收敛文案。
- `bus.ts` `emitExtended` 复制了 `emitDurable` 的 seq+append+broadcast 段（仅多 `ignorable:true`）——正是阶段十七「冗余整改」要清的形态，可把 ignorable 透传合一。
- `permission/rules.ts` `patternToRegex` 每次匹配现编译正则，`evaluate` 每条规则编译两次（action+resource），无 memo。
- `bus.ts` `pushRing` 溢出静默丢最老（容量 256），无「你丢了 N 条需重同步」信号；token 洪流下慢消费者有真实溢出可能。
- `connection.ts` 之外，`lsp/manager.ts` 的 LSP 方法名仍是字面量（仅 publishDiagnostics 取协议常量）。

### 架构取向上的隐忧
1. `@spark/protocol` 已承载 reducer / SSE 状态机 / HTTP transport / 页面 controller / flow-rows / 文案表 / 键位表 / 命令描述符，硬约束只有「零依赖 engine」，**无体积与职责上界** —— 最易腐化处。
2. 「事件种数六处文档同步」= 这些正文不是从源码派生的；契约用例与文档站词表页已做生成，两条路线并存。
3. 测试金字塔与架构承诺错配：四端 parity 是核心承诺，而 web 3,528 / mobile 675 / miniapp 688 / desktop 71 行测试——承诺最重处验证最薄。
4. **缺跨层不变量测试载体**：现有测试全在单层内。建议补「turn.completed 后不得存在 status==='running' 的 tool 项、不得存在未闭合 streaming 项」的不变量断言。
