## 2. 总体判定

**这个项目有两张脸，得分差距很大。**

- **作为工程纪律实验：接近满分。** 架构 invariants 落到代码、自我审计真做、AI 协作元系统超规格——这三件事同时做到的仓库，我见过的极少。
- **作为软件产品：未经验证，且有明显的过度建设症状。** 它现在是一台精密的、没有任何证据表明有人在用的机器。

一句话：**工程素养 9/10，产品判断 4/10。** 本项目证明了作者（及其指挥的 AI 军团）能造出结构正确的东西；尚未证明这个东西值得被造出来。

## 3. 真实优势（三项，全部有证据）

### 3.1 骨架是对的，且不变量落到了代码里

"引擎 headless，UI 是事件流的投影"不是口号。durable/live 二分、单写者 JSONL、审批 fail-closed、协议先行的 zod 合同 + MockTransport 对等（AGENTS §1.1），这些是整个 agent harness 领域真正重要的 invariants，本仓把它们做成了代码约束而非文档愿望。选这条路造 agent 工作台，方向判断正确。

### 3.2 自我审计是真的做了

doc/05（G1–G7）、doc/07（H01–H36）、doc/11（LA 系列）不是摆设。doc/11 §4.10 对 38 张工单逐张对账，自己查出 12 张打折、3 张证伪——**一个愿意用源码核查自己"声称完成"的项目，比十个只会勾 checklist 的项目健康。** 这是本仓最珍贵的资产。

### 3.3 AI 协作元系统是超规格的

AGENTS.md + skills + `scripts/check_doc_links.py` + CI 七关，等于把"怎么管 AI 代理"本身做成了基础设施；规则放置四分类（AGENTS 管项目 / DESIGN 管视觉 / SKILL 管流程 / 专属文件管工具差异）是清醒的设计，不是摆设。

## 4. 系统性问题（六项）

### 4.1 AI 批量生产节奏：产量曲线即风险曲线

838 个提交集中在 2026 年 9 月一个月（36,895 行 TS）。这个密度不可能是人类边写边思考的速度，它是多 AI 代理并行生产的特征。含义很直接：**仓内没有任何证据表明这些代码被真实使用过**——无使用报告、无问题反馈痕迹、无 dogfooding 记录。doc/11 自己查出约 30% 工单完成度打折，与产量曲线预测一致。CI 全绿不等于可用：CI 验证的是"与规格一致"，不是"规格是对的"。

（仓外是否有用户，仓内不可证，需人类确认；但即便有，38 单对账里 15 单打折/证伪的比例也说明"写完即声称完成"的模式真实存在。）

### 4.2 文档主体化与元系统维护税

约 12,651 行 markdown 对 36,895 行 TS，比值对正常项目是病态的。更贵的不是行数，是同步税：

- 事件词表计数漂移史：21→19→20→21→22→26→27→34→35，三次人工修正后才上 CI 硬检查（AGENTS §4.1 自认"历史上反复飘移过三次"）。
- AGENTS.md 版本表 75 行，记录的是 AI 会话编年史；`CLAUDE.md` 至今写着"硬性约定十二条"，而 AGENTS §2 现有 14 条 + 3a 条——shim 漂移实例现成摆着。

元系统本身在不断产生需要元系统维护的问题。这是内耗，不是资产（超过一定量之后）。

### 4.3 功能面对成熟度严重超配

约 28 条命令 × 35 种事件 × 四个端，外加 MCP、LSP、arena、goals、hooks 13 挂点、computer-use、voice、桌面自更新。每加一种事件，四端 reducer、mock、契约测试、五处文档计数都要动（AGENTS §4.1 自己总结的"六处活"）。**一个人都没有的产品，扛着 35 种事件的长期兼容负担**，是在为想象中的用户预支成本。

### 4.4 路线图由参考项目驱动，而非用户驱动

11 个参考项目 + Claude Code 泄露源码仓逐个在线解剖，"可抄的全部写进工单"（AGENTS v1.70）。效率很高，但功能列表的驱动力是"别人有的我们不能没有"，不是"Spark 的用户需要什么"。这是缝合怪式 roadmap：它保证了技术完备性，不保证产品方向。

### 4.5 引擎门面巨石 engine.ts

详见 §5 专节。AGENTS §1.1 记 3161 行、R-D 判决"不再拆"——本报告认为该判决的预设已被持续违反，提案重审。

### 4.6 外部验证缺位

eval 仅 ScriptedLlm 回归集（确定性场景，测的是"没退步"不是"做得好"）；doc/09 论证了不接 Terminal-Bench/SWE-bench。两条都自有其理，但合起来的后果是：**本项目没有任何外部标尺可以回答"这个 agent 到底行不行"。** 对内，doc/11 的对账是替代品，但它只查"声称 vs 代码"，不查"代码 vs 现实"。

## 5. engine.ts 专节：门面巨石的三个具体问题与拆法

`packages/engine/src/engine.ts`，3157 行、约 189 个方法。先给公道话：**委托代码本身写得很干净**——薄委托给 `arenaManager`/`settings`/`metrics`/`memory` 等的部分无聊、可读、无花样，符合 ARCHITECTURE §9 的 boring code 原则。问题在组织方式，不在代码质量。

### 5.1 问题一：重要逻辑被埋在约 100 个薄委托里

- `wireSession`（会话装配核心逻辑）：`engine.ts:2695`，320 行
- `createSession`：`engine.ts:878`；`resumeSession`：`engine.ts:1164`；`forkSession`：`engine.ts:1248`；`rollbackToCheckpoint`：`engine.ts:2410`；`handleOf`：`engine.ts:3015`
- 而 `listMemories`、`resetUsage`、`renderMetrics` 这类两行委托（`engine.ts:2317` 起一带）就散布在同一文件里

任何想理解会话生命周期的人（或 AI 代理），得先滚过一百个委托才能找到入口。**文件的每一行都在收取"发现成本"。**

### 5.2 问题二：该在专门模块里的逻辑，门面里又长了一份

`packages/engine/src/` 下已有 `session/`（7 文件，含 `runtime.ts`/`tree.ts`/`scan.ts`）、`permission/`、`feedback/`、`secrets/`、`automation/`、`arena/`、`embedding/`、`model-catalog.ts`。但门面里仍然握着：

- `projectLayerFor`/`readProjectRulesLenient`（`engine.ts:1439`–1500）——项目级权限规则加载，而 `permission/service.ts` 就在旁边
- `resolveModelRef`/`resolveModel`（`engine.ts:3067`–3124）——模型解析，旁边就是 `model-catalog.ts`

这是门面巨石的标准腐化路径：逻辑一旦住进门面，正式归属模块就再无法独立演进——改模块不影响门面里的副本，副本随即开始漂移。`engine.ts` 已从 2871 行长到 3157 行，住的每一条逻辑都在加速这个循环。

### 5.3 问题三：全仓冲突最集中的一个文件

`apps/server` 几乎所有路由最终调 `engine.xxx()`。再叠加本仓的工作方式——**多个 AI 代理在同一仓库并行开工**（git log 里 ZCode/Qoder/Trae/Claude 混签）——一个 3157 行的共享门面意味着：任何碰会话生命周期的工单都要改它，并行会话互相冲突，且**没有任何单个代理能把 3157 行整本读进上下文做可靠编辑**。一个"给 AI 代理用的仓库"（AGENTS.md 的立身之本），留着这样一个文件，是自相矛盾的。

### 5.4 拆法提案（三步，按性价比排序；只提案，待晚风拍板后开工）

**第一步——只搬真逻辑，API 形状不变**（server 零改动，契约测试天然兜底）：

| 目的地 | 搬迁内容（engine.ts 行号） | 预计减行 |
| --- | --- | --- |
| `session/lifecycle.ts`（新文件） | create/resume/fork/rollback/wireSession/handleOf/requireEntry/findSessionFile/scanForkChildren/treeOf/checkpointsOf | ~700 |
| `permission/` | projectLayerFor / readProjectRulesLenient | ~80 |
| `model-catalog.ts` | resolveModelRef / resolveModel | ~60 |
| `embedding/` | embeddingEnabled / semanticPort 引导 | ~80 |

剩下的纯委托本就该留在门面——门面就是 API 面，留着是对的。第一步不解决全部问题，但把"难找的核心逻辑"从"一百个委托"里解放出来，且零调用方改动、零行为变更。

**第二步**（收益递减）：剩余委托按域收成子门面对象（`engine.sessions`/`engine.settings`/`engine.storage`…），`Engine` 变组合器。动 server 调用点，独立工单。

**第三步**（可选）：评估 server 改指向子门面，进一步缩小单文件冲突面。

### 5.5 与既有判决的关系

AGENTS §1.1（v1.58 起）记"管理面透传属对外 API，R-D 判决不再拆"。本报告认为：该判决在约 2900 行时成立；文件已到 3157 行且持续增长，"不再拆"正在变成"不许拆"，其代价（发现成本、模块腐化、并行冲突）已大于收益（API 面稳定）。按 AGENTS §7"不确定的设计决策……让人类决策"，本报告不自行翻案，登记为待决项 D-Q1（见 §7），请晚风裁决。

## 6. 整改优先级建议

1. **砍功能面**：38 单对账打折的功能先做可用性复核，没用的挂起而非继续加。四端 × N 功能的矩阵，任何一格退化都是负债。
2. **拆 engine.ts 第一步**（§5.4）：纯搬迁、行为不变、CI 契约测试兜底，是当前性价比最高的代码整改。
3. **冻结文档扩张**：按 §2.14 自己的 2000 行规则办；修 `CLAUDE.md` 的"十二条"漂移这类 shim 卫生。
4. **找真实用户**：没有第 4 项，前三项都是给机器上油。

## 8. 结论

Spark 的骨架和纪律是这个作者最值钱的东西；它现在最大的风险不是技术做不出来，而是**在没有一个真实用户的情况下，用 AI 批量生产的节奏持续加功能、长文档、养巨石**。下一步如果不是砍面、拆巨石、找人真用，而是继续按工单库往下推，这些精致的机制只会一起烂掉。把 3157 行的门面拆小、把功能面收窄、把文档冻住——三件事都不难，难的是承认"还没证明值得被造出来"，然后按 §6 的顺序动手。
